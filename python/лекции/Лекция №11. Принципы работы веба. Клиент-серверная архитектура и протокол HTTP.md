# 1. Что такое веб и как работает интернет

Начнём с простого вопроса: что происходит, когда пользователь вводит адрес сайта в браузере и нажимает Enter?

Например:

```
https://example.com
```

На первый взгляд всё просто: браузер открывает сайт. Но на самом деле за этим действием стоит целая последовательность процессов.

Веб (World Wide Web, WWW) — это система взаимосвязанных документов и ресурсов, доступ к которым осуществляется через интернет с использованием специальных протоколов.

Важно понимать разницу:

- Интернет — глобальная сеть, объединяющая компьютеры и другие устройства.
    
- Веб — одна из служб, работающих поверх интернета.
    
- Браузер — программа, позволяющая получать и отображать веб-ресурсы.
    
- Веб-сервер — программа, которая принимает запросы и отправляет ответы.
    

Например, электронная почта, онлайн-игры и передача файлов также используют интернет, но не обязательно используют веб.

## 1.1. Из чего состоит адрес сайта

Рассмотрим адрес:

```
https://example.com:443/products?id=15
```

Он состоит из нескольких частей:

|Часть|Значение|
|---|---|
|`https`|Протокол передачи данных|
|`example.com`|Доменное имя|
|`443`|Порт сервера|
|`/products`|Путь к ресурсу|
|`?id=15`|Параметры запроса|

Разберём каждую составляющую.

Протокол определяет правила обмена информацией между клиентом и сервером.

Доменное имя — удобное текстовое обозначение адреса сервера. Например, `example.com`.

Порт — номер логической точки подключения к серверу. Для HTTP обычно используется 80, для HTTPS — 443.

Путь указывает, какой именно ресурс запрашивается.

Параметры позволяют передавать дополнительные данные серверу.

Например:

```
https://shop.ru/products?id=15&category=phones
```

Здесь серверу передаются два параметра:

- `id=15`;
    
- `category=phones`.
    

## 1.2. Как доменное имя превращается в IP-адрес

Компьютеры взаимодействуют друг с другом, используя IP-адреса.

Однако человеку неудобно запоминать адреса вида:

```
142.250.185.14
```

Поэтому используются доменные имена.

Для преобразования доменного имени в IP-адрес применяется DNS (Domain Name System).

Упрощённо процесс выглядит так:

1. Пользователь вводит `example.com`.
    
2. Компьютер обращается к DNS-серверу.

# 2. Клиент-серверная архитектура

Большинство современных веб-приложений построено на клиент-серверной архитектуре.

Клиент — программа или устройство, которое отправляет запросы и получает результаты.

Сервер — программа или компьютер, который принимает запросы, обрабатывает их и отправляет ответы.

Примеры клиентов:

- браузер Google Chrome;
    
- мобильное приложение;
    
- программа на Python;
    
- JavaScript-код на веб-странице.
    

Примеры серверов:

- веб-сервер Nginx;
    
- приложение на Python Flask;
    
- приложение на Python FastAPI;
    
- сервер базы данных MySQL.

## 2.1. Как происходит взаимодействие

Представим, что пользователь открывает страницу авторизации.

Последовательность действий:

1. Пользователь вводит логин и пароль.
    
2. Браузер формирует запрос.
    
3. Запрос отправляется на сервер.
    
4. Сервер получает данные.
    
5. Сервер проверяет их.
    
6. При необходимости обращается к базе данных.
    
7. Формирует ответ.
    
8. Отправляет ответ браузеру.
    
9. Браузер отображает результат.
    

Например, если данные правильные, пользователь попадает в личный кабинет. Если неправильные — получает сообщение об ошибке.

Важно: браузер не должен самостоятельно решать, правильный ли пароль ввёл пользователь. Проверка должна выполняться на сервере.

- Database хранит информацию о товарах и покупателях.
    

## 2.3. Статические и динамические веб-страницы

Веб-страницы можно условно разделить на два типа.

Статические страницы — содержимое которых заранее подготовлено и обычно не меняется в зависимости от пользователя.

Например:

```html
<!DOCTYPE html>
<html>
<head>
    <title>Моя страница</title>
</head>
<body>
    <h1>Привет, мир!</h1>
    <p>Это статическая страница.</p>
</body>
</html>
```

Сервер просто отдаёт готовый HTML-файл.

Динамические страницы — содержимое которых формируется с учётом определённых условий или данных.

Например, пользователь открывает личный кабинет и видит своё имя, список заказов и баланс.

Сервер получает данные из базы и формирует соответствующий ответ.

# 3. Протокол HTTP

HTTP (HyperText Transfer Protocol) — протокол прикладного уровня, который определяет правила взаимодействия между клиентом и сервером при передаче веб-данных.

Проще говоря, HTTP определяет:

- как клиент должен обращаться к серверу;
    
- какие данные можно передавать;
    
- как сервер должен отвечать;
    
- как сообщать об ошибках;
    
- как передавать информацию о типе содержимого.
    

HTTP работает по модели «запрос — ответ».

## 3.1. HTTP и HTTPS

Существует две основные версии протокола, с которыми сталкивается обычный пользователь.

|HTTP|HTTPS|
|---|---|
|Передача данных без встроенного шифрования|Передача данных с использованием TLS|
|Обычно порт 80|Обычно порт 443|
|Данные могут быть прочитаны при перехвате трафика|Данные защищены шифрованием|
|Не обеспечивает конфиденциальность соединения|Обеспечивает конфиденциальность и проверку подлинности сервера|

HTTPS — это HTTP, работающий поверх защищённого соединения TLS.

Например, при авторизации на сайте необходимо использовать HTTPS, чтобы логин и пароль не передавались в открытом виде.

Важно: HTTPS не означает, что сам сайт безопасен. Он защищает канал связи, но не гарантирует отсутствие ошибок в приложении.

## 3.2. Особенность HTTP — отсутствие состояния

HTTP является stateless-протоколом, то есть сам по себе не хранит состояние предыдущих запросов.

Представим ситуацию:

1. Пользователь вошёл в личный кабинет.
    
2. Открыл другую страницу сайта.
    
3. Перешёл в каталог товаров.
    

Каждый запрос HTTP рассматривается независимо от предыдущего.

Но как тогда сайт понимает, что пользователь уже авторизован?

Для этого применяются дополнительные механизмы:

- Cookies;
    
- Sessions;
    
- токены авторизации (например, JWT).
    

Например, браузер может хранить идентификатор сессии в Cookie и автоматически отправлять его вместе с последующими запросами.

# 4. Структура HTTP-запроса

HTTP-запрос — сообщение, которое клиент отправляет серверу для получения информации или выполнения определённого действия.

Рассмотрим пример:

```
GET /products?id=15 HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html
```

Запрос состоит из нескольких частей.

1. Стартовая строка.
    
2. Заголовки.
    
3. Пустая строка.
    
4. Тело запроса (если присутствует).

## 4.1. Стартовая строка

```
GET /products?id=15 HTTP/1.1
```

Она содержит три элемента:

|Элемент|Значение|
|---|---|
|GET|Метод запроса|
|/products?id=15|Адрес запрашиваемого ресурса|
|HTTP/1.1|Версия протокола|

## 4.2. Заголовки запроса

Заголовки (Headers) содержат дополнительную информацию о запросе.

Например:

```
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html
```

Рассмотрим наиболее распространённые заголовки.

|Заголовок|Назначение|
|---|---|
|Host|Имя целевого хоста|
|User-Agent|Информация о клиенте|
|Accept|Какие типы данных клиент готов принять|
|Content-Type|Формат передаваемых данных|
|Content-Length|Размер тела запроса|
|Authorization|Данные авторизации|
|Cookie|Передача Cookie|
|Referer|Адрес страницы, с которой пришёл запрос|

Например:

```
Content-Type: application/json
```

Означает, что тело запроса содержит данные в формате JSON.

## 4.3. Тело запроса

Тело запроса (Body) используется для передачи данных на сервер.

Например, при регистрации пользователя:

```
POST /register HTTP/1.1
Host: example.com
Content-Type: application/json

{
    "username": "student",
    "password": "123456"
}
```

Здесь:

- `POST` — метод отправки данных;
    
- `/register` — адрес обработчика;
    
- `Content-Type` — формат передаваемой информации;
    
- JSON — сами данные пользователя.
    

Тело запроса присутствует не у всех методов.

# 5. Методы HTTP-запросов

Метод HTTP определяет, какое действие клиент хочет выполнить над ресурсом.

Это один из важнейших элементов HTTP.

Рассмотрим основные методы.

|Метод|Назначение|Пример|
|---|---|---|
|GET|Получить информацию|Получить список пользователей|
|POST|Передать данные, создать ресурс|Зарегистрировать пользователя|
|PUT|Полностью заменить ресурс|Обновить данные пользователя целиком|
|PATCH|Частично изменить ресурс|Изменить только email|
|DELETE|Удалить ресурс|Удалить пользователя|
|HEAD|Получить заголовки без тела ответа|Проверить наличие файла|
|OPTIONS|Узнать доступные параметры взаимодействия|Узнать разрешённые методы|

## 5.1. GET

Используется для получения информации.

Например:

```
GET /users HTTP/1.1
Host: example.com
```

Сервер может вернуть список пользователей:

```
[
    {
        "id": 1,
        "name": "Иван"
    },
    {
        "id": 2,
        "name": "Пётр"
    }
]
```

GET обычно не должен изменять состояние данных на сервере.

## 5.2. POST

Используется для передачи данных серверу, часто для создания нового ресурса.

Например:

```
POST /users HTTP/1.1
Host: example.com
Content-Type: application/json

{
    "name": "Александр",
    "age": 20
}
```

Сервер получает данные и может создать нового пользователя.

## 5.3. PUT

Используется для полной замены существующего ресурса.

Например:

```
PUT /users/15 HTTP/1.1
Host: example.com
Content-Type: application/json

{
    "name": "Александр",
    "age": 21
}
```

Сервер заменяет представление пользователя с идентификатором 15 переданными данными.

## 5.4. PATCH

Используется для частичного изменения ресурса.

Например:

```
PATCH /users/15 HTTP/1.1
Host: example.com
Content-Type: application/json

{
    "age": 22
}
```

В этом случае изменяется только возраст пользователя.

## 5.5. DELETE

Используется для удаления ресурса.

```
DELETE /users/15 HTTP/1.1
Host: example.com
```

Сервер получает команду удалить пользователя с идентификатором 15.

## 5.6. Идемпотентность HTTP-методов

Есть ещё одно важное понятие — идемпотентность.

Идемпотентный запрос — это запрос, повторение которого несколько раз приводит к тому же результату, что и выполнение один раз (с точки зрения предполагаемого эффекта на сервере).

Например:

- GET — идемпотентный.
    
- PUT — идемпотентный.
    
- DELETE — идемпотентный.
    
- POST — обычно неидемпотентный.
    
- PATCH — зависит от конкретной операции.
    

Пример: если удалить пользователя с ID 15 один раз, он будет удалён. Повторное удаление не должно привести к дополнительному изменению состояния.

А вот если отправить POST-запрос на создание заказа пять раз, можно получить пять заказов.

# 6. HTTP-заголовки

Заголовки позволяют клиенту и серверу передавать дополнительную информацию.

Рассмотрим основные категории.

### Заголовки запроса

Передают информацию от клиента серверу.

Примеры:

```
User-Agent: Mozilla/5.0
Accept: application/json
Authorization: Bearer token123
```

### Заголовки ответа

Передают информацию от сервера клиенту.

Примеры:

```
Content-Type: application/json
Content-Length: 150
Server: nginx
```

### Универсальные заголовки

Могут использоваться как в запросах, так и в ответах.

Например:

```
Cache-Control: no-cache
```

Управляет поведением кеширования.

Ещё один пример:

```
Connection: keep-alive
```

Позволяет поддерживать соединение открытым для последующих запросов в HTTP/1.1.

## 6.1. Content-Type

Особенно важно понимать назначение этого заголовка.

Он определяет тип содержимого передаваемого сообщения.

|Значение|Описание|
|---|---|
|text/html|HTML-документ|
|text/plain|Обычный текст|
|application/json|JSON|
|application/xml|XML|
|image/png|PNG-изображение|
|image/jpeg|JPEG-изображение|
|application/pdf|PDF-документ|
|multipart/form-data|Данные формы, в том числе файлы|

Например, сервер возвращает JSON:

```
HTTP/1.1 200 OK
Content-Type: application/json

{
    "status": "success"
}
```

Благодаря заголовку браузер или другая программа понимает, какой тип данных был получен.

# 7. HTTP-ответ

HTTP-ответ — сообщение, которое сервер отправляет клиенту после обработки запроса.

Пример:

```
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 25

{
    "status": "success"
}
```

Ответ состоит из:

1. Стартовой строки.
    
2. Заголовков.
    
3. Пустой строки.
    
4. Тела ответа.
    

## 7.1. Стартовая строка ответа

```
HTTP/1.1 200 OK
```

Она содержит:

|Элемент|Значение|
|---|---|
|HTTP/1.1|Версия протокола|
|200|Код состояния|
|OK|Текстовое описание|

## 7.2. Тело ответа

В теле ответа сервер передаёт результат обработки запроса.

Это может быть:

- HTML-страница;
    
- JSON;
    
- XML;
    
- изображение;
    
- документ;
    
- обычный текст.
    

Например, при запросе информации о пользователе сервер может вернуть:

```
{
    "id": 15,
    "name": "Александр",
    "role": "student"
}
```

# 8. Коды состояния HTTP

Код состояния (Status Code) показывает результат обработки запроса сервером.

Все коды разделены на пять основных групп.

## Пять групп HTTP-кодов

## 1xx

Информационные

Промежуточная информация

## 2xx

Успешные

Запрос успешно обработан

## 3xx

Перенаправления

Требуется дополнительное действие

## 4xx

Ошибки клиента

Проблема в запросе клиента

## 5xx

Ошибки сервера

Проблема при обработке на сервере

## 8.1. Группа 1xx — информационные

Промежуточные ответы, которые сообщают клиенту о ходе обработки запроса.

Например:

- `100 Continue` — клиент может продолжить отправку запроса.
    
- `101 Switching Protocols` — сервер согласился переключить протокол.
    

## 8.2. Группа 2xx — успешное выполнение

Самая приятная группа кодов.

|Код|Название|Значение|
|---|---|---|
|200|OK|Запрос успешно выполнен|
|201|Created|Ресурс успешно создан|
|202|Accepted|Запрос принят для обработки|
|204|No Content|Запрос выполнен, тело ответа отсутствует|

Примеры:

- Пользователь запросил список товаров — `200 OK`.
    
- Пользователь зарегистрировался — `201 Created`.
    
- Сервер принял задачу на обработку — `202 Accepted`.
    
- Пользователь удалил запись — `204 No Content`.
    

## 8.3. Группа 3xx — перенаправления

Сервер сообщает, что для получения нужного ресурса необходимо выполнить дополнительное действие.

|Код|Название|Значение|
|---|---|---|
|301|Moved Permanently|Постоянное перенаправление|
|302|Found|Временное перенаправление|
|304|Not Modified|Ресурс не изменился|
|307|Temporary Redirect|Временное перенаправление с сохранением метода|
|308|Permanent Redirect|Постоянное перенаправление с сохранением метода|

Например, пользователь открывает старый адрес сайта:

```
http://example.com
```

Сервер отвечает:

```
HTTP/1.1 301 Moved Permanently
Location: https://example.com
```

Браузер переходит по новому адресу.

## 8.4. Группа 4xx — ошибки клиента

Означает, что запрос не может быть обработан из-за проблемы на стороне клиента.

|Код|Название|Значение|
|---|---|---|
|400|Bad Request|Некорректный запрос|
|401|Unauthorized|Требуется аутентификация|
|403|Forbidden|Доступ запрещён|
|404|Not Found|Ресурс не найден|
|405|Method Not Allowed|Метод не поддерживается для ресурса|
|409|Conflict|Конфликт состояния|
|422|Unprocessable Content|Содержимое запроса не прошло проверку|
|429|Too Many Requests|Слишком много запросов|

Особенно важно различать:

401 Unauthorized — пользователь не прошёл аутентификацию или не предоставил необходимые учётные данные.

403 Forbidden — сервер понял запрос, но запрещает доступ к ресурсу.

Например, пользователь вошёл в систему, но пытается открыть административную панель, к которой у него нет доступа. Сервер возвращает `403 Forbidden`.

## 8.5. Группа 5xx — ошибки сервера

Показывает, что сервер столкнулся с проблемой при обработке корректного запроса.

|Код|Название|Значение|
|---|---|---|
|500|Internal Server Error|Внутренняя ошибка сервера|
|501|Not Implemented|Функциональность не реализована|
|502|Bad Gateway|Некорректный ответ от вышестоящего сервера|
|503|Service Unavailable|Сервис временно недоступен|
|504|Gateway Timeout|Тайм-аут ожидания ответа|

Например, пользователь отправляет запрос, а приложение Python обращается к базе данных. Если база данных недоступна и приложение не может обработать запрос, сервер может вернуть `500 Internal Server Error` или другой подходящий код в зависимости от причины.

# 9. Практический пример: как выглядит полный обмен HTTP

Теперь объединим всё изученное.

Представим, что у нас есть сайт с каталогом товаров.

Пользователь открывает:

```
https://shop.example.com/products
```

Браузер отправляет запрос:

```
GET /products HTTP/1.1
Host: shop.example.com
Accept: application/json
User-Agent: Mozilla/5.0
```

Сервер обрабатывает запрос, обращается к базе данных и возвращает:

```
HTTP/1.1 200 OK
Content-Type: application/json

[
    {
        "id": 1,
        "name": "Ноутбук",
        "price": 50000
    },
    {
        "id": 2,
        "name": "Смартфон",
        "price": 30000
    }
]
```

Теперь пользователь хочет создать заказ.

Браузер отправляет:

```
POST /orders HTTP/1.1
Host: shop.example.com
Content-Type: application/json

{
    "product_id": 1,
    "quantity": 2
}
```

Сервер проверяет данные, создаёт заказ и возвращает:

```
HTTP/1.1 201 Created
Content-Type: application/json

{
    "order_id": 125,
    "status": "created"
}
```

Таким образом, мы видим полный цикл:

- Клиент формирует запрос.
    
- Сервер принимает запрос.
    
- Обрабатывает данные.
    
- При необходимости обращается к базе.
    
- Возвращает ответ с кодом состояния и данными.
    

# 10. Практическая демонстрация в Python

Чтобы закрепить материал, посмотрим, как можно отправить HTTP-запрос из Python.

Для этого используем библиотеку `requests`.

Установка:

```
pip install requests
```

Получение информации:

```
import requests

response = requests.get(
    "https://jsonplaceholder.typicode.com/users"
)

print("Код ответа:", response.status_code)
print("Заголовки:", response.headers)

users = response.json()

for user in users:
    print(user["name"])
```

Здесь:

- `requests.get()` отправляет GET-запрос.
    
- `response.status_code` возвращает код состояния.
    
- `response.headers` содержит заголовки ответа.
    
- `response.json()` преобразует JSON в Python-объект.
    

Отправка данных:

```
import requests

data = {
    "title": "Новая запись",
    "body": "Текст записи",
    "userId": 1
}

response = requests.post(
    "https://jsonplaceholder.typicode.com/posts",
    json=data
)

print(response.status_code)
print(response.json())
```

Здесь мы отправляем POST-запрос с JSON-данными.

Обратите внимание: `requests` автоматически формирует необходимые заголовки для передачи JSON при использовании параметра `json`.
